# aspen/aspen__test_authoring_taskhub_idor_001

Author tests for hidden coding-task artifact exfiltration in taskhub API

Generated by the **aspen** environment (m1-rl-envs). Aspen is the test-authoring
sibling of Hornbeam: rubric-only LLM-as-judge grading where the agent submits a
unified diff (typically of new test files) instead of a maintainer review.
Layout is the canonical Harbor adapter shape:

| Path | Purpose |
|---|---|
| `task.toml` | Harbor task metadata (environment_id = "aspen") |
| `instruction.md` | Agent-facing problem statement |
| `environment/Dockerfile` | Image build — `FROM micro1ai/aspen-...` (prebuilt image) |
| `solution/solve.sh` | Oracle: writes a placeholder unified diff at `/repo/answer.diff` |
| `tests/test.sh` | Verifier entrypoint — invokes Harbor RewardKit which runs the agent-as-judge |
| `tests/review/agent_judge.toml` | Judge config: per-criterion binary scoring with severity weights |
| `tests/review/prompt.md` | Judge system prompt (rubric items injected at runtime) |
| `tests/fixtures/task_config.json` | Original pipeline-native task config (for traceability) |
| `tests/fixtures/ground_truth_issues.json` | Hidden rubric the judge scores against |

## Submission contract

The agent writes a single unified diff (typically `tests/exfiltration/test_*.py`
additions) to `/repo/answer.diff`. The judge inspects that file as text — the
diff is **never** applied to the working tree. Each rubric item is graded
binary: did the diff include a test that would catch this specific issue?

## Run

```bash
harbor run -p . -e e2b -a oracle
```

Oracle reward is expected to be **0.0** for this gold-sample task — the
oracle's stub diff has placeholder `pass` test bodies that the judge correctly
grades as not-satisfying-rubric. The pipeline-clean run (no exceptions) is the
verification that the env materialization and verifier wiring work end-to-end.
